# P4 model deployment and assisted classification — in progress

P3's user-approved safe manual workflow is accepted; **P4 is not complete**. These previews are read-only: they do not authorize any file move or copy. Manual file operations have their separate P3 evidence.

## Explicit removal of active Windows model data (2026-10-06)

Settings now offers **Remove active model data**, showing a read-only directory/asset list before a separate permanent-removal confirmation. Only application-installed, generated model directories on Windows NTFS with the application-pinned manifest are eligible. File-space overlaps, aliases found through native directory IDs, unverifiable local boundaries, changed directory identity and stale workspace revisions are refused. Non-Windows entry points report unavailability and perform no deletion.

`ModelAssetRemoval` reads the bounded manifest through a no-follow handle, opens every existing listed asset with retained native handles, refuses unsupported streams/content and verifies all hashes before the first deletion. Deletion acts on those handles, never a path-based recursive tree. The directory, manifest, licenses/notices, caches and unknown files remain. A cataloged hard link outside the model folder remains readable when the model-side link is removed. Missing assets allow retry; modified/locked assets prevent the preflight from completing. A filesystem failure after deletion begins can leave a partially removed model—this is not an all-or-nothing or power-loss protocol, and there is no Undo claim.

The existing coordinator holds OrganizationGate and the metadata gate, refuses retained user-file recovery evidence, clears the model selection on successful removal and checkpoints its backup. The UI cancels model work and pauses observation first. Failures retain the confirmation/error rather than claiming success; the preserved manifest supports checking remaining files again. No new workspace schema or parallel file executor was introduced.

Nine focused Core cases passed (`model-removal-final.trx`), covering pinned-only deletion, unknown/nested/user-file preservation, cataloged hard-link survival, changed bytes, revision/manifest mismatch, delete-denying handles, replaced root, overlap, cancellation, recovery refusal and backup agreement. The existing actual-package UI fixture passed read-only plan/cancel/confirm, real asset removal, selection clearing and unchanged workspace history/content (`model-data-removal-ui.log`, MODEL_DATA_REMOVAL_VERIFIED and terminal Success). It removes only an isolated installation created by that test. App Release build has zero warnings/errors; five notices have twelve-language parity. No full P3 matrix or package rerun. Native Unix removal, arbitrary model families, old-version discovery and cache/staging deletion remain unsupported. Stale LSP consumer-type findings were contradicted by the compiling/passing code, not suppressed by weakening it.

## Resumable partial-cache relocation (2026-10-06)

Changing model location can now preserve an incomplete download when its bounded sidecar contains a valid strong ETag. Complete verified caches are tried first across the previous/legacy locations; only then are partial caches considered. Data and ETag are copied under the same cooperating-download ownership lock, using create-new destinations and keeping the original. The ETag is published after the data copy: interruption cannot turn partial bytes into a verified model. Weak, absent, wildcard or unusable validators do not authorize migration, and existing destination data/sidecars are not overwritten by this copy step.

The normal downloader still requires exact Range/If-Range/Content-Range/length agreement and the final pinned SHA-256 before installation. A migrated partial is only resumable state, not an authenticated/verified artifact. No active-model setting changes until the existing installation/loading/save workflow succeeds, and nothing is deleted.

Eleven focused small protocol cases passed (`partial-cache-transfer.trx`), including strong/weak/missing ETags, copying and subsequent Range=3 continuation, unchanged original bytes, and sidecar-collision refusal. The deliberately short response remains a failure, not a completed download. A separate real-package case proved a complete verified cache wins over an earlier partial source and remains reusable with a network-refusing client (`partial-cache-priority.trx`). Twelve-language location copy was updated. No live model download, full P3 suite, CI or package repetition for this increment.

## Download cache follows model installation (2026-10-06)

New downloads use `.desknext-downloads` under the selected installation location. Before a network request, the online/repair command can copy a complete pinned archive from the previously activated model's cache or the legacy application-data cache. It verifies the source, uses exclusive create-new output, bounds copied bytes, verifies the destination and leaves the source untouched. Existing destination files are not overwritten by migration; partial/unverified old caches are not copied. A copied complete archive can be used offline through the existing downloader/installer. Failed or cancelled copies remain as partial cache data; this is not atomic relocation or a new cleanup protocol, and retrying an incomplete destination can require a normal network restart.

The cache location is derived from the activated generated model-directory name, including a trailing-separator-safe parent lookup. No workspace fields/schema or extra configuration store were added. Changing the installation destination is still a draft, and only saving the verified installed model makes that location survive reopening. The active cache is excluded by both observation collection and the Core pending-record boundary. Old caches/models and interrupted files are not automatically deleted; permanent model removal remains open.

Two focused tests passed with the real pinned ZIP (`model-cache-copy.trx`): no mutation for absent/partial/cancelled sources, complete-cache copy, network-refusing offline reuse, no overwrite, and retained original after mid-copy cancellation. The existing UI workflow seeded a complete legacy cache and invoked the actual online/repair entry with network proxy access intentionally unavailable; installation, CPU loading, explicit activation/reopening and observation exclusions passed (`model-cache-location-com.log`, Success/ModelPackageActivationVerified/FolderObservationVerified true). ## Bounded Jev rate-limit retries (2026-10-05)

Jev now retries only an explicit HTTP 429 refusal, at most twice (three attempts total) within the existing 45-second deadline. It honors Retry-After seconds or dates; a server wait longer than ten seconds is returned to the user instead of shortened. Missing headers use one/two-second backoff. Each attempt has a fresh request message with the same question payload. Cancellation stops the wait before another send. HTTP 401/503, network failures and invalid response bodies do not automatically repeat a potentially billable POST.

The twelve-language Jev setup notice explains this policy. Eleven focused client tests passed (`artifacts/p4-installer-tests/jev-rate-limit.trx`), covering identical payloads, the attempt cap, long waits, no 503 retry, cancellation and existing schema/privacy checks. No real Jev API request was made. This supersedes the earlier blanket no-automatic-POST-retry statement only for explicit rate limiting; it is not live API or billing acceptance.

## Usable path

Choose a trusted offline Laya model bundle directory (containing `manifest.json`) with **Browse** in Settings, or enter its path, then use the existing **Save settings** action. Choosing/cancelling only edits the draft; no download or inference starts. Select **Laya · Local CPU**, save settings, then use **Classification preview** in a file row's context menu. No file content enters the request and no file or workspace mutation is performed.

Frames are capped at 1 MiB, diagnostics retained up to 4096 characters, and each preview has a two-minute deadline. Cancellation and normal exit release the worker. Request ID/revision, probability consistency, and the current workspace revision are checked before display.

The existing model hash/provenance check is reused, **not publisher authentication**. Only explicitly selected, trusted local bundles are supported; no network download, Python discovery, GPU selection, or cloud fallback was introduced. The one-shot worker cold-loads on each preview; no latency or memory acceptance is claimed.
