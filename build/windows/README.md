# DeskNext Windows development package

This is an **unsigned development package**, not a signed release installer. It runs without Python or an installed .NET SDK. The model is downloaded/imported separately and is not included. CPU inference binaries are isolated under `worker/cpu`; GPU variants are not enabled by this package.

Extract the complete archive to a local folder, open PowerShell in that folder, and run:

```powershell
powershell.exe -NoProfile -File .\Install.ps1
```

The script prints the installed application's full path. The default installation is `%LOCALAPPDATA%\Programs\DeskNestPreview\versions\<version>`. Launch `DeskNest.App.exe` from that printed path. If local execution policy blocks scripts, use your organization's approved execution policy; the installer does not change it.

To upgrade, close DeskNext and run the installer from a newer extracted package. Each version occupies a separate directory; existing versions remain available for code rollback. Launching older code against newer workspace schemas is subject to Core's schema checks and may be refused. This installer never rewrites workspace schemas or automatically rolls back user data.

Uninstall application payloads with:

```powershell
powershell.exe -NoProfile -File .\Install.ps1 -Action Uninstall
```

The uninstaller verifies owned payload files before deleting them. It preserves workspace settings, transaction evidence, managed files, model caches, and any unknown files placed inside the installation. Modified payloads or locked files stop removal with an error. It does not force-close DeskNext. A validated removal plan is saved before deletion, so after closing the locking application you can repeat `-Action Uninstall` to finish a partial removal. Missing files are accepted only with that persisted plan, not in an ordinary damaged installation. All remaining planned files are verified again before removal resumes.

The schema-2 ownership record and lock file intentionally remain after successful removal. Repeated uninstall is safe; installing again can reuse this owned root. A preexisting version directory is never overwritten: if unknown files kept an old version directory alive, use a different package version or manually reconcile those retained files before reusing that version. Unknown files elsewhere in the installation root do not prevent reinstallation. Genuinely unowned directories remain ineligible.

For an interrupted install, rerun with the exact same package. Initial package validation occurs before the installation root is created; a new root is published with ownership already present. Pending ownership precedes staging and version publication, so a published-but-uncommitted version can be verified and adopted on retry. Individual copies use verified temporary files and no-overwrite renames. Modified staged/published files cause refusal rather than being overwritten. Abandoned `.copy-*.tmp` files inside the installation root and `.desknest-bootstrap-*` siblings are retained for manual diagnosis, not recursively cleaned. Corrupt ownership requires manual reconciliation; the installer never falls back to a possibly stale ownership backup.

`Test-Install.ps1`, `Test-InstallRecovery.ps1` and `Test-Publish.ps1` exercise synthetic fixtures, injected interruption checkpoints, a real delete-denying file handle, manifest symlinks (explicitly skipped if OS privileges are unavailable), and side-effect-free refused packaging retries. They do not prove power-loss durability, handle-bound resistance to same-user path-replacement races, or clean-machine/signed-release installation.

Developers can build a separate **test-only** package with `Publish-Windows.ps1 -Version 0.3.0-probe -IncludeRecoveryProbe`, then run `Test-Package.ps1 -Bundle artifacts/packages/0.3.0-probe/DeskNest-win-x64 -NativeWindow -RecoveryProbe` from the repository. This requires Node.js and a .NET SDK on the developer machine, not on end-user machines. The installed probe is force-killed and restarted only against fresh isolated temp roots. Its twenty cases cover uncommitted and committed file/directory moves, real coordinator rename/recovery-area deletion blocked before metadata commit, interrupted coordinator undo, experimental copies interrupted both before metadata enrollment and after its backup checkpoint, and a real journal-sharing fault after file/directory rename. Interrupted undo must restore the previously committed forward location, not falsely complete the undo. An unenrolled copy interruption must preserve the source, published copy and immutable intent, require manual reconciliation, and never silently enroll or delete the destination. A checkpointed copy must preserve both objects and its original publication receipt; restart may clear its intent only after verifying that durable receipt. The latter cases stop at a trusted test-only pre-acknowledgement barrier in the internal coordinator. Production manual Copy/Paste supports cataloged Windows NTFS items with managed or existing mapped targets; the interruption callbacks remain internal and test-only. The passive observer verifies that reading a journal does not block its atomic replacement. Separate fault cases intentionally hold a deny-write/delete journal handle, verify that a physical rename occurred but the Prepared receipt could not advance, then kill and restart; recovery must retain the journal and destination and require manual reconciliation without fabricating rollback. Two reverse-rename cases deny the Restored checkpoint after the rollback fence was saved; restart must preserve the already-restored source, receipt and fence, without pretending rollback completed. The two staged-copy cases terminate after a flushed first 64 KiB block of a larger file: restart preserves source, partial staging and intent, refuses publication/adoption and blocks a following move. This callback exists only on internal test-visible copy code and is never read from user metadata. The test checks the exact case names and successful termination/recovery results, then verifies uninstall removed both App and probe executables. Default packages do not contain the probe; this test exercises packaged Core recovery, **not** the installed GUI's drag/undo flow or power-loss recovery.

The separate `Test-Package.ps1 -ManualWorkflow` option runs the installed GUI with `--native-window-smoke --manual-workflow`. It uses its real native clipboard and the production workspace commands to catalog isolated file/directory fixtures, create new managed destinations, cut/paste and undo. It **requires an empty clipboard** and refuses without overwriting existing clipboard content. It does not launch Explorer or inject physical input, and does not prove cross-application drag/drop. This option is explicit for local runs; hosted Windows CI opts in. The result must include both `ManualWorkflowVerified` and `NativeClipboardRoundTripVerified` as literal true.

For a local **real desktop screenshot**, build the App in Release, then run `powershell.exe -NoProfile -File build/windows/Capture-UiReview.ps1` from the repository. This developer-only script opens an isolated Chinese sample workbench, space window and capsule briefly, captures their bounding rectangle from the Windows desktop, and closes them. It writes `desktop-composite.png`, `capture.json` (native handles, observed scale and transparency level) and the terminal probe log under a timestamped `artifacts/ui-review/native-*` directory. It does not touch the real workspace or clipboard or change display settings. At least 1370×740 logical pixels are required; no resolution is forced. The screenshot may contain other desktop content between windows, so keep these ignored artifacts private. It is not headless rendering, and does not establish multi-DPI, physical input, Mica/Acrylic or release acceptance. The capture script is not included in application payloads.

For **real Explorer drag/drop**, run `powershell.exe -NoProfile -File build/windows/Test-ExplorerDrag.ps1` from an **unelevated** terminal after a Release build. Keep the mouse idle during this opt-in test. It opens isolated file/directory fixtures in new Explorer windows, injects OS drag gestures in both directions, and uses production commands to confirm import and undo. It never uses the clipboard, refuses to drive preexisting Explorer windows and restores the pointer afterwards. At least 1100×600 logical pixels are needed. Logs under `artifacts/p3-publication-tests/explorer-*` must contain terminal `Success=true` and `ExplorerDragVerified=true`; failed fixture roots are retained. Normal Explorer cannot drop into an elevated app. To exercise an already installed build, pass `-App 'C:\path\to\installed\DeskNest.App.exe'` from a fresh unelevated terminal. The fixture creates a new managed space through the existing dialog command before its first drag. The driver checks the target HWND is visible at the drop point and starts on the Explorer item's icon/name area. Same-process post-install driver failures have been observed; a fresh-driver pass is not a diagnosis of them. This local developer script is not included in application payloads and is not complete cross-platform, GUI-crash or release acceptance.

For the disabled Flow-definition editor, developers may compile `native/pogget-bridge` with CMake in Release (use `-DCMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded` on Windows), then supply the resulting absolute DLL path to `Publish-Windows.ps1 -PoggetNativeLibrary <path-to-desknest_pogget.dll>`. Source builds accept `dotnet build src/DeskNest.App -p:PoggetNativeLibrary=<absolute-path>`. The DLL is copied beside the app; JSON definitions cannot select a library. Without it, native validation and saving definitions remain unavailable. This supplies definition validation and explicit reviewed runs: literal prompts and individually confirmed moves of cataloged regular files into existing space folders. The existing Core coordinator owns moves and undo. Other file/control execution and automatic triggers remain unavailable; existing published packages are unchanged.

Checksums detect corruption; this unsigned manifest does **not** establish publisher authenticity. Do not treat it as the final P7 signed installer or an authenticated update feed. Physical Windows 10/ARM64 and macOS/Linux install/upgrade/uninstall evidence is separate from this win-x64 development package.
